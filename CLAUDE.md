# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A web app for sharing unlisted YouTube videos with friends, laid out like YouTube (thumbnail grid split into admin-managed category shelves + watch page with player). Meant to run on a home LAN server, not the public internet — see `README.md` for the hosting/firewall steps. Login is passwordless for regular accounts; only admin accounts need a password (see below).

## Commands

```bash
npm run dev      # start dev server (Turbopack) on :3000
npm run build    # production build — also type-checks and generates .next/types
npm run start    # serve the production build; binds 0.0.0.0 by default (see README)
npm run lint     # ESLint (flat config, eslint.config.mjs)
```

There is no test suite configured.

`LayoutProps<'/route'>` / `PageProps<'/route'>` (used in every `layout.tsx`/`page.tsx`) are generated by Next into `.next/types`. Running `tsc --noEmit` directly without a prior `next build`/`next dev` will falsely report them as missing — use `npm run build` to typecheck.

## Architecture

**Runtime**: Next.js 16 (App Router, Turbopack) on Node 25, React 19. Node 25 is new enough that Next's own generated `AGENTS.md` (imported above) warns training-data knowledge of Next may be stale — this was confirmed firsthand: Next 16 renamed the `middleware.ts` convention to `proxy.ts` (old name now warns as deprecated). This repo uses `src/proxy.ts`, not `middleware.ts`.

**Database**: `node:sqlite` (Node's built-in `DatabaseSync`, not `better-sqlite3` — chosen specifically to avoid a native-module/node-gyp build step on Windows). Single connection, cached on `globalThis` in `src/lib/db.ts` so dev-mode HMR doesn't accumulate connections. Schema lives as one `CREATE TABLE IF NOT EXISTS` string in that same file and is (re-)applied on every connection open — there is no migration tool. `PRAGMA busy_timeout` is set because `next build` opens the DB from multiple parallel worker processes; without it they fail each other with "database is locked".

Adding a column to an *existing* table needs more than editing the `CREATE TABLE IF NOT EXISTS` string — that statement is a no-op once the table already exists, so a live install's DB never sees the new column. `ensureColumn()` in `db.ts` runs a guarded `ALTER TABLE ... ADD COLUMN` (checked via `PRAGMA table_info`) for cases like this; the `videos.category` column was added this way and backfills existing rows via its `DEFAULT`.

⚠️ **`node:sqlite` rows have a null prototype**, not `Object.prototype` — confirmed by `Object.getPrototypeOf(row) === null`. React Server Components refuse to pass such objects as props into Client Components ("Only plain objects... can be passed to Client Components"), so any DB row reaching a `"use client"` component (e.g. `<VideoForm video={video} />`) throws at request time — not at build time, so it's easy to miss until you actually click into that page. `queryAll`/`queryOne` in `db.ts` guard against this by spreading every row (`{ ...row }`) into a real plain object before returning it; don't bypass those helpers with raw `db.prepare(...).get()/.all()` calls without doing the same.

**Auth is passwordless for viewers, password-protected for admins**: the login form (`src/app/login/LoginForm.tsx`) always shows username + display name + an optional password field; `signInOrRegister` in `src/lib/auth.ts` decides whether the password matters. An unrecognized username is created on the spot as a `viewer` — no password involved. The **first account ever created becomes admin automatically**; after that, admin status is granted either by another admin (`/admin/users`) or by listing the username in the `ADMIN_USERNAMES` env var at login time. Whenever the resolved account is (or is about to become) an admin, a password is required:
- Admin account with `password_hash` already set → the submitted password must verify (scrypt + `timingSafeEqual`, salted per-user; see `hashPassword`/`verifyPassword` in `auth.ts`) or login is rejected.
- Admin account with **no** password yet (freshly promoted, freshly auto-created as the first user, or reset by another admin) → whatever password was submitted this time becomes the new one, in the same request, no separate "set password" screen. `resetPassword()` (exposed in `/admin/users` as "비밀번호 초기화") just nulls out the hash/salt so this path re-triggers on the account's next login.

Sessions are server-side rows in the `sessions` table plus an httpOnly cookie (not JWT), so blocking a user in `/admin/users` invalidates their session immediately. Note a session, once issued, does **not** re-check the password — password verification only happens at login time.

**Two-tier auth check — don't collapse these**:
- `src/proxy.ts` only checks whether the session *cookie is present* and redirects to `/login` if not. It cannot do more than that: the proxy/edge runtime can't reach `node:sqlite`.
- `requireUser()` / `requireAdmin()` in `src/lib/auth.ts` (called at the top of every server component/page and Server Action that needs it) do the real DB-backed check — valid session, not expired, correct role.
- Because of this split, `src/lib/auth.shared.ts` exists just to hold the `SESSION_COOKIE` name so `proxy.ts` can import it without pulling in `auth.ts` (which is marked `server-only` and touches the DB).

**Route layout**:
- `src/app/(viewer)/` — the YouTube-like shell (`Header` + `Sidebar` in its `layout.tsx`) wrapping `/` (grid, supports `?q=` search, `?tag=`, and `?category=`), `/watch/[id]`, `/history`, and `/videos/new` (video *creation* — open to any logged-in user, not admin-only, see below).
- `src/app/admin/` — separate layout gated by `requireAdmin()`: video *editing* (`/admin`, `/admin/videos/[id]/edit`), category CRUD (`/admin/categories`), and account management (`/admin/users`). There is no `/admin/videos/new` — it was removed in favor of `/videos/new` when video creation stopped being admin-only.
- `src/app/actions/{auth,videos,users,categories}.ts` — all mutations go through Server Actions; there are no API route handlers.

**Video permissions are split finer than "admin vs. everyone else"** — this is easy to get wrong by copy-pasting a `requireAdmin()` call:
- **Create** (`createVideoAction`) and **fetch metadata** (`fetchVideoMetadataAction`) only need `requireUser()` — any logged-in account, admin or viewer, can add a video from `/videos/new`.
- **Delete** (`deleteVideoAction`) needs `requireUser()` plus an ownership check: admins can delete any video, a viewer can only delete a video where `video.added_by === user.id`. The delete button itself lives on the watch page (`src/components/DeleteVideoButton.tsx`), conditionally rendered by the same check, *not* in the admin video list.
- **Edit** (`updateVideoAction`) and **pin/unpin** (`togglePinAction`) are still `requireAdmin()`-only — editing someone else's listing and reordering the home page are curation actions, deliberately not opened up when creation was.
- `added_by` (the FK to the creating account) is what ownership checks compare against — don't confuse it with `uploader_label`, a free-text "credit" field the submitter can type in independently (e.g. crediting whoever appears in the video, which may not be the account that added it).

**Data layer** (`src/lib/`): `db.ts` (connection + raw query helpers) → `videos.ts` / `users.ts` / `categories.ts` (query functions, all `server-only`) → Server Actions call these directly. `youtube.ts` is deliberately *not* `server-only`: it's pure URL-parsing (`parseYouTubeId`, `thumbnailUrl`, `embedUrl`) reused client-side by `src/components/VideoForm.tsx` (shared by both `/videos/new` and `/admin/videos/[id]/edit` — despite the similar name, it does *not* live under `components/admin/` since it's no longer admin-exclusive) to show a live thumbnail preview as a link is pasted, before the form is submitted.

**Data model** (`src/lib/db.ts`): `users` (role: `admin`|`viewer`; `password_hash`/`password_salt` nullable — only admins ever have these set), `sessions`, `categories` (admin-managed, ordered by `sort_index`; seeded once with "앨범"/"추천영상" — see `ensureDefaultCategories()`), `videos` (`category` is a free-text column matching a `categories.name`, *not* a foreign key — same "string label, no join" style as `tags`; validated against the live category list at the Server Action layer in `readInput()`/`categoryExists()` instead of a DB constraint), `watch_events` (composite PK `user_id, video_id`, upserted on each watch — powers both the history page and the "N명이 봄" viewer count), `comments` (flat, no replies — `user_id`/`video_id` both `ON DELETE CASCADE`).

**Home page** (`src/app/(viewer)/page.tsx`): with no `?q=`/`?tag=`/`?category=` filter active, it renders one shelf per row from `listCategories()`, in `sort_index` order — add a category in `/admin/categories` and a new shelf appears automatically, no code change needed. Any filter present collapses this into a single flat result grid instead (search/tag can still match videos from any category). A category can't be deleted while videos still reference it (`deleteCategory()` guards on `countVideosInCategory`), and the last remaining category can't be deleted either. Metadata auto-fetch for the admin form (`src/lib/youtubeMetadata.ts`, key-free: title via YouTube's oEmbed endpoint, description scraped best-effort from the watch page's `<meta name="description">`) is unrelated to this split but lives in the same admin video form.

**Images**: thumbnails are loaded directly from `i.ytimg.com` via `next/image`; the remote pattern is allow-listed in `next.config.ts`. `hqdefault.jpg` is used deliberately over `maxresdefault.jpg`, which 404s for lower-resolution source videos.
